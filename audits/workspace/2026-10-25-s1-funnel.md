# S1 v2 signal funnel: why there are only 51 signals and 27 trades (2026-10-25)

Run `01a173d8-4d7e-751c-a141-1ee97f748458`: strategy version `aac4fda7` on point-in-time NIFTY 500, 2016-01-01 to 2021-12-31. The report shows 102 watchlisted rows, 51 signals, 24 rejections (20 `add_to_loser`, 4 `max_positions`) and 27 trades.

**Verdict: the low count comes from strict rules, not from a code or data bug.** The VCP detector removes 99.7% of trend-template passers. Of the few that pass, 71% are already above their pivot and are dropped. The 20 `add_to_loser` rejections fire correctly: each is the scan republishing the stale pivot of a name the bot already holds. A few design issues are listed below. None of them is a direction, unit or threshold bug.

## Method

Everything here uses the engine's own code paths, run read-only against `hat_live`. Scratch scripts are in `/data/workspace/scratch-btui/funnel/`.

- **Market loading.** The market is loaded with `backtest.data.load_market`, exactly as `runs.backtest_bot` does, using the run's universe version and the stored config. The DB config is identical to `s1-v2-draft.yaml` except for the default `entry_timing`.
- **Scan inputs.** `ScanInputs` is built as in `loop._publish` and `watchlist.scan_and_publish`: `MarketView.window`, the regime closes, the features and the series. Members come from `_tradable_members` on the run's own sqlite ledger (`backtest.ledger.ledger`).
- **Evaluation.** Each member is evaluated with `strategy.scoring.evaluate_playbook`, the same call `scan._scan_playbook` makes. VCP internals come from `criteria.vcp` (`_read_base`, `contraction_chain`, `build_contractions`).
- **Coverage.** Every one of the 1,486 scan nights was evaluated, not only the samples.
- **Reproduction check.**
  - The rows passing on gate-on nights total **102**, the same as the report's `watchlisted`.
  - Rows whose next-session high exceeds the pivot total **51**, the same as `signals`.
  - Of those 51, rows on a name already held total **20**, the same as `add_to_loser`.
  - `scan_bot` itself agrees on the spot-checked night.

## 2. Sanity check: big stage-2 winners

I took trend-template passers that were in a base of at least 15 bars and had among the largest 126-session forward total returns. For each, the table shows what VCP said each night from the base until the stock left the base (after which `base_too_short` applied). Depths are the last contractions in percent; "dry" is the final contraction's volume against the pre-base average.

| Name (base) | Engine verdict through the base | Why |

## 3. The 20 `add_to_loser` rejections fire correctly but are an artefact of republishing

**The rule.** `risk/decision.py:352` rejects the signal when any open position of the bot in the same instrument is a loser. `risk/caps.py:119-121` defines a loser as `last_price < avg_entry`. In the backtest, `last_price` is the previous close, marked (`backtest/loop.py:838` and `engine/snapshot.py:118`).

**What happens.** The scan does not exclude names the bot already holds (`engine/scan.py:190` evaluates every member). After an entry, the same base and pivot persist until a new swing forms. Whenever the name closes back at or below the pivot, `close_vs_pivot` passes again and the row is republished with the same pivot. If the next day's high crosses it, the result is a new signal.

**Why it is always `add_to_loser`.** The previous close is at most the pivot, and the average entry is pivot + 1 tick + slippage. So every re-signal on a held name is a loser by construction, and `position_exists` (line 353) can never fire for this setup.

**Verified.** All 20 rejected signals are on held names with the original pivot:

| Name | Re-signals |
|---|---|
| SIS (Sep–Oct 2021) | 6 on consecutive days |
| SKSMICRO | 3 |
| VIPIND | 2 |
| IBSEC | 2 |
| WIPRO | 2 |
| POWERGRID | 2 |
| TATAPOWER | 1 |

The other 4 rejections (`max_positions`) are CHENNPETRO ×2, IBSEC and COCHINSHIP.

**The same mechanism causes re-entries after an exit at the identical stale pivot.** These are counted as new trades:

| Name | Entries at the same entry price and stop |
|---|---|
| VIPIND | 2, both at 362.7741 / 343.50 |
| COCHINSHIP | 3, all at 190.8059 / 181.075 |
| FINCABLES | 2 |

So 27 trades are about 22 distinct setups. This is not a risk-engine bug. It is a missing rule in the scan: no exclusion for names already held, and no expiry for a pivot that has already broken out and failed.

## 4. Bugs vs. strictness

### Checked and found correct (no bug)

- **Trend template direction.** All SMA comparisons are strict `>`. `pct_from_52w_low` uses the 52-week low and `pct_from_52w_high` the 52-week high, in the right directions (`criteria/setup.py`).
- **Units.** `min_turnover` is in INR crore against INR `traded_value`. `min_price` reads the raw close.
- **Disabled criteria and the score threshold.** Disabled criteria are skipped before scoring (`strategy/scoring.py:92`), so the two disabled `rs_rank` instances do not dilute the threshold.
- **VCP can clear the threshold.** A passing VCP scores at least (1 + 0.5 + 0.5 + 0.5)/4 = 0.625 (`criteria/vcp.py:170-189`), above 0.6. Observed scores are 0.68–0.84.
- **Dry-up baseline window.** It is the 50 sessions before the base start (`vcp.py` `_read_base`, `last(..., offset=len-start)`), which is correct.
- **Volume.** It is not dividend-scaled; only `_SCALED` prices are (`backtest/data.py:283`).

### Design issues (strictness or semantics, not code defects)

1. **The last-6 tightening rule is the binding VCP constraint.**
   - `vcp.py:160-167` judges the most recent `contractions[1]` (6) contractions, and `vcp.py:200` requires every consecutive ratio to be ≤ 0.75.
   - There is no noise floor (`min_depth_pct` is unset) and the swing detector uses 3 bars.
   - So any base with an early deeper leg fails forever, and a clean three-leg VCP preceded by noise is rejected.
   - Of the 20,441 ratio failures, 714 had a tightening suffix of at least 3 legs, and 448 of those also met the final-depth (≤10%) and dry-up (≤0.7) limits. They were rejected only because of older legs.
2. **`vcp` is configured `mode: score`, but it is effectively hard.**
   - A failed VCP exposes no `pivot` (levels come only from passed criteria, `scoring.py:94`), so `close_vs_pivot` fails with `no_pivot` (`setup.py:369`).
   - The weight of 2.0 and the 0.6 threshold are cosmetic for this config.
3. **Pivot-confirmation lag.**
   - The final contraction's low is a swing low only after 3 higher bars, so price has often already crossed the pivot by then.
   - With `close_vs_pivot.max_above_pct: 0`, 71% of VCP passes are dropped.
4. **The pivot sits well inside the base.**
   - The pivot is the final contraction's high. For watchlist rows it sits a median **7.6%** below the base's highest high (interquartile range 6.8–10.6%), because `max_high_spread_pct` is off.
   - Entries are therefore "breakouts" in the middle of the base. This plausibly contributes to 17 of 27 exits on `close_below_sma`. It is a quality issue, not a count issue.
5. **Stale-pivot republishing** (section 3).
6. **Minor.**
   - `sma_above 50>200` (order 5) is redundant after 150>200 and 50>150. The `tt4` and `tt5` counts are identical on every night.
   - The ₹10 cr turnover floor is nominal and not scaled for time.

## Which single knob most raises the signal count

These are single-knob variants, each run through `evaluate_playbook` on every trend-template-passer night (gate on). The trend template is unchanged. "Next-day breaks" is the backtest's trigger proxy, which matched `signals` exactly at baseline.

| Variant | Watchlist rows | Next-day breaks (≈ signals) | Distinct names |
|---|---|---|---|
| baseline | 102 | 51 | 31 |
| `final_depth_max_pct: 15` | 102 | 51 | 31 |
| `min_depth_pct: 3` | 113 | 51 | 30 |
| `lookback_days: 60` | 137 | 73 | 42 |
| `dryup_vs_avg50: 1.0` | 168 | 78 | 46 |
| `contractions: [3, 3]` (judge only the last 3 legs) | 236 | 121 | 65 |
| `pivot_window: 2` | 238 | 96 | 67 |
| `pivot_source: base_high` | 371 | 10 | 55 |
| `depth_ratio_max: 1.0` | 655 | 266 | 135 |
| **`contractions: [2, 6]`** | **1,430** | **462** | **238** |

**The single knob that raises the signal count most is `vcp.contractions` from [3, 6] to [2, 6]: about 9× the signals (462 next-day breaks, 238 names).** It also admits much weaker two-leg "patterns".

The more targeted fix for the defect seen in the sanity names is `contractions: [3, 3]`, which judges only the latest three legs. It is about 2.4× (121 breaks) and keeps the three-leg tightening requirement.

Either change should be paired with excluding held names and expiring failed pivots in the scan (section 3); otherwise the extra signals add more same-pivot re-entries.

I ran no backtest; none of these variant counts has been traded.
