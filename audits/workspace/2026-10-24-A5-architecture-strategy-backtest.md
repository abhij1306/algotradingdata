# architecture audit: engine/strategy, engine/criteria, engine/portfolio, backtest/  (2026-10-24, main @ 1a7aa75)

## Summary
The criteria registry, config model, scoring and the pure allocator/lifecycle/regime are deep, well-tested modules, and the backtest really does call the live engine for the scan, entries and exits. The friction is in the parts *around* a playbook: what kind of playbook it is, which levels it triggers on, and which inputs its stop and entry filters get. Each is decided by a hard-coded name or assembled by hand in three places (scan, live, backtest), so a new strategy that is just "criteria + seed YAML" can silently fail to trade live, pass the evidence gate on a backtest that skipped its edge, or size under another strategy's numbers. Fix first: F1 (playbook kind keyed on the name `episodic_pivot`), because it also decides what the backtest models and what the lifecycle gate refuses. The hard-coded strategy-name tables (caps, policy, `SLEEVE_OF_STRATEGY`, `SEED_NAMES`) are being consolidated in another PR and are not reported here. F3 is the identity question that PR needs to settle.

## Findings

### F1. Playbook kind, live routing and backtest fidelity are keyed on the playbook name, not on what the playbook uses   [High] [Confirmed] [Strong]
Files: engine/scan.py:42, engine/scan.py:252, engine/live_entry.py:259, daily/intraday.py:294, backtest/loop.py:602, backtest/spec.py:62-80, data/gapscan.py:59-60, engine/criteria/__init__.py:38-114, engine/strategy/versions.py:72-97
Problem: `EP_PLAYBOOK = "episodic_pivot"` decides four things: the nightly scan skips the playbook (scan.py:252), the pre-open path builds candidates only for it (live_entry.py:259, intraday.py:294), the backtest skips it (loop.py:602), and `GAP_PLAYBOOKS` names only it as unbacktested, so only it is refused by the lifecycle gate (spec.py:80). Each criterion type already declares `data_needs` (`preopen`, `live_bars`, `announcements`), but nothing except `sync_criterion_types` reads it. Two concrete failures follow for a new strategy:
(a) A gap/pre-open playbook with any other name (say `gap_and_go`, setup `neglect` and trigger `gap_up`) is scanned nightly as if it were a breakout. Its rows have no `pivot`, so live fires `level_undefined` and the backtest skips `no_trigger_level`. It never trades and no gap names it.
(b) A nightly playbook whose edge is in its trigger criteria (`volume_pace`, `catalyst_attached`, a daily-bar trigger) is backtested as a bare level break. The gap `trigger_is_level_break_only` "names no playbook" (spec.py:77-79), so the Research -> Backtested gate passes it on evidence that never ran its trigger.
The EP selector is also hard-coded apart from the config: the gap scan keeps gaps of at least 10% in bands 10/20 (`EP_MIN_GAP_PCT`, `EP_BANDS`), whatever `gap_up.min_pct` the playbook sets, so a config with `min_pct: 5` never sees a 5-10% gapper.
Fix: deepen the criteria registry into the one authority on a playbook's needs. Derive `playbook_kind(playbook)` (nightly-watchlist vs pre-open) from its criteria's `data_needs`, or make it an explicit config field validated against them. Derive `unmodelled(playbook)`, the criteria the daily-bar loop cannot evaluate, from the same data. Then the scan, the live pre-open path and the backtest branch on the kind, and `known_gaps` and `GAP_PLAYBOOKS` are computed per run from the config rather than a static tuple. Pass the gap-scan minimum from the configs' `gap_up` params, the lowest across EP playbooks.
Tests: pure tests of `playbook_kind` and `unmodelled` over the two seeds and over one renamed EP playbook; a test that `known_gaps(spec)` names a playbook carrying `volume_pace`.
Size: M

### F2. A playbook's trigger-time inputs (stop inputs, entry-filter context) are assembled by hand in three places, and live shares one ATR/swing length across all bots   [High] [Confirmed] [Strong]
Files: daily/market.py:141-152, daily/market.py:170, daily/market.py:237-263, daily/assembly.py:248-254, engine/trigger.py:409-458, engine/trigger.py:461-478, backtest/loop.py:515-546, backtest/loop.py:669-692, engine/scan.py:127-176
Problem: `stops.plan_stop` is a clean seam, but each caller builds its `StopInputs` its own way: the backtest uses an `isinstance` chain per rule with a per-rule length (loop.py:515-546); live uses `DailyInputs` from `DailyData` (trigger.py:430-442); the scan uses `getattr(playbook.stop, "lookback_days", 0)` (scan.py:172). Live computes one ATR length and one swing lookback for every active bot's live version (`stop_lengths`, market.py:141-152, over `_configs` in assembly.py:248). When two bots disagree, that input is None, every such stop skips `stop_input_missing`, and no entry is taken. A new strategy, or even a new shadow version of an existing strategy, whose `atr_multiple.days` or `swing_low.lookback_days` differs from another bot's therefore switches off ATR or swing stops for every bot live. The backtest reads the right length per rule (`view.atr(..., rule.days)`), so its evidence never shows this. The entry filters have the same split. Live passes the full `LiveContext` (`plan_entry`, trigger.py:444-451), while the backtest builds one from six fields (`entry_filter_context`, trigger.py:461-478). A new entry filter that reads `adv20`, `prev_close`, `cum_volume` or `levels` gets `no_data` and rejects every backtest entry while it passes live, or the reverse for a filter written against the backtest.
Fix: make one module own "the inputs a playbook needs at a trigger": `stop_inputs(rule, source, instrument, day, entry, day_lows)` over a small `DailySource` protocol (`atr(length)`, `lows(lookback)`, `final_contraction_low`), implemented by `DailyData` and `MarketView`. Live then computes ATR and swing per rule length (a lazy per-length cache in `DailyData` instead of `stop_lengths`). Declare the entry-filter context fields in one function both callers use, so a new filter's inputs are added in one place.
Tests: a pure test that two configs with ATR 14 and 20 each get their own ATR from `DailyData`, which now returns None; a test that the backtest and live builders give the same `StopInputs` for the same bars, rule and entry.
Size: M

### F3. A strategy has two identities, `config.bot` and `HatStrategy.name`, and nothing ties them together   [High] [Confirmed] [Strong]
Files: engine/strategy/versions.py:147-168, engine/portfolio/allocation_service.py:89, backtest/spec.py:238, backtest/loop.py:259, backtest/loop.py:565, backtest/evidence.py:365, engine/live_entry.py:182, engine/live_entry.py:267, backtest/ledger.py:69, admin.py:421-449
Problem: Live allocation keys a sleeve's base weight by `strategy.name` (allocation_service.py:89). The risk defaults (`strategy_key`: `p_max`, `max_chase`), the backtest's sleeve weight and the evidence's base-weight check all key by the config's `bot:` field (live_entry.py:182/267, spec.py:238, loop.py:259, evidence.py:365). `save_draft` never checks that `config.bot` equals the strategy's name. Adding a strategy means copying a seed YAML, and if its `bot:` line is left unchanged the new strategy sizes under the copied strategy's `p_max` and `max_chase`. Its backtest sizes at the copied strategy's base weight, while live allocates by the new name, so either the evidence fails `backtest_off_base_weight` or it passes against the wrong weight. There is also no admin command to create a strategy row: `seed-strategies` iterates `SEED_NAMES`, so a new strategy still needs a code edit after the consolidation PR unless that PR derives the list from the seeds directory.
Fix: one identity. Either refuse `save_draft` when `config.bot != strategy.name` (`bot_name_mismatch`) or drop `bot` from the config and pass the strategy name wherever `config.bot` is read. Make sure the consolidation PR's single authority keys on that one name. Add a `create-strategy --config x.yaml` admin command (or seed from the directory listing) so a new strategy needs no code.
Tests: `save_draft` refuses a mismatched `bot`; the backtest `sleeve_weight` and the live allocation resolve the same key for one strategy.
Size: S-M

### F4. Trigger levels are a closed set spread over six modules, and the backtest triggers on `row.pivot` whatever the playbook's level expression says   [Medium] [Confirmed] [Strong]
Files: engine/criteria/live.py:28-35, engine/criteria/live.py:65, engine/criteria/live.py:143-158, engine/scan.py:44, engine/scan.py:203, engine/live_entry.py:189-197, engine/trigger.py:557-563, backtest/loop.py:569, backtest/loop.py:620, backtest/loop.py:645
Problem: A setup criterion publishes levels through `extras` generically (`scoring.numeric_levels`), but only three names survive to a trigger. `LEVEL_KEYS` keeps pivot, consolidation_high and final_contraction_low on the watchlist row. `price_breaks_level.level` is a `Literal` of three expressions resolved by an if-chain. `live_entry` and `TriggerMonitor.context` each copy pivot and consolidation_high by name. The scan then writes `pivot = pivot or consolidation_high` into the single `pivot` column, and the backtest uses that column as the level, the max-chase reference and the slot rank for every playbook. A new setup that exposes, for example, `flag_high` needs edits in all six places before it can trigger, and its backtest triggers on whatever `pivot` happened to hold.
Fix: let the scan store every numeric level of the passed stages (it already computes them), let `price_breaks_level` take a small expression (`name` or `max(a, b)`) validated against the levels its playbook's setup criteria declare, and give the backtest one `resolve_level(playbook, row_levels)` that live calls too. Daily-bar runs read the opening range as unavailable, already a known gap.
Tests: `resolve_level` over a config using a new level name; config validation refuses a level no setup criterion of the playbook exposes.
Size: M

### F5. One regime multiplier table, keyed "momentum", serves every sleeve   [Medium] [Confirmed] [Worth exploring]
Files: engine/portfolio/regime.py:37-43, engine/portfolio/regime.py:216, engine/portfolio/regime_service.py:144-153, engine/portfolio/allocation_service.py:80-92, backtest/spec.py:207-224
Problem: The regime spec says each sleeve has a multiplier per confirmed state (regime.py:4), but the stored model has only `multipliers.momentum`, `regime_table` reads only that key, and `run_allocation` applies the same value to every bot. A non-momentum strategy (mean reversion, say) cannot get its own regime response without code changes in regime.py, regime_service.py, allocation_service.py and the backtest's `RunSpec.regime_table`. Both seeds are momentum today, so nothing is wrong yet.
Fix: key the table by a sleeve attribute (`hat_bot.risk_cluster` already exists, or a `regime_profile` in the policy) with `momentum` as the default; `regime_table(model, profile)` returns that profile's row and `RunSpec` records the profile it sized under.
Tests: `regime_table` returns a second profile's row; the allocator gets different `regime_table_value`s for two profiles.
Size: S-M

### F6. The backtest is single-sleeve, so account-level caps run against the sleeve's capital and none of this is a listed gap   [Medium] [Confirmed] [Worth exploring]
Files: backtest/loop.py:300-317, backtest/loop.py:578, daily/entries.py:145-164, risk/decision.py:403-407, backtest/spec.py:62-74
Problem: Live `total_equity` is the sum of every sleeve's book (daily/entries.py:145-151), and the global open-risk cap counts every bot's positions of the same mode (decision.py:403). The backtest passes the sleeve's own capital as `total_equity` (loop.py:578), its cluster is the sleeve alone (loop.py:308), and only its own positions exist. Cross-sleeve binding of global open risk, the cluster cap and the owner-level slots therefore never appears in evidence. `KNOWN_GAPS` does not list it. Adding a third strategy changes how often those caps bind live, and no run measures that.
Fix: at minimum, add a fixed gap code (`single_sleeve_caps`) to `KNOWN_GAPS` so every run reports it. Later, a portfolio run that drives several sleeves' `_Run`s over one ledger and one `total_equity`, as a research tool rather than a gate.
Tests: none beyond the gap code being reported.
Size: S (gap code), L (portfolio run)

### F7. Two release state machines share state names, and `versions.py` changes for four unrelated reasons   [Medium] [Confirmed] [Worth exploring]
Files: engine/strategy/versions.py:1-17, engine/strategy/versions.py:72-97, engine/strategy/versions.py:171-283, engine/strategy/versions.py:347-457, engine/portfolio/lifecycle.py:20-39, engine/portfolio/lifecycle.py:279-321, engine/portfolio/sleeve_service.py:212-252
Problem: A strategy version moves draft -> backtested -> shadow -> live -> retired, with its own 20-session shadow gate (`promote_version` -> `shadow_gate`). A sleeve moves research -> backtested -> shadow -> live -> probation -> retired, with another 20-session shadow gate (`_shadow_edge`), and Live needs the version to be live (sleeve_service.py:230-236). The same words mean different gates: a version's "backtested" needs only a `for_promotion` run, while a sleeve's needs DSR, PBO, span and gap checks. Taking one new strategy to real money is about seven owner steps across two machines and two shadow clocks. `versions.py` (506 lines, 12 commits in 60 days) also holds the criterion-catalogue sync, the seeds, bot creation and `release_overview`. This is a decided staging rule (decisions.md "Earn real money in stages"), so the finding is the duplication, not the stages.
Fix: keep both gates but name the version states differently (e.g. `frozen`/`trial`/`released`), or make the version's shadow period derive from the sleeve that runs it so there is one shadow clock. Split `versions.py` into `catalogue.py` (sync), `release.py` (version gate), and move `create_bot`/`add_sleeve`/`seed_default_bots` to `portfolio/sleeve_service.py`.
Tests: existing pure gate tests carry over; no new ceremony.
Size: M

### F8. `ENTRY_SKIP_REASONS` hand-lists the entry-filter types, so a new filter's rejection is stored as `invalid_input`   [Low] [Confirmed] [Strong]
Files: engine/entries.py:87-100, engine/entries.py:136-149, engine/trigger.py:481-497
Problem: `evaluate_entry_filters` returns the failing filter's type as the skip reason, and `_skip_decision` keeps it only if it is in a hand-kept set naming `adtr_filter` and `max_chase`. A new `entry_filter` criterion still rejects (fail closed), but its signals are stored and reported as `invalid_input`, which hides the real reason in digests and shadow analysis.
Fix: build the set from the registry: `{t.code for t in REGISTRY.values() if t.stage == "entry_filter"}` plus the stop and pending codes.
Tests: a new registry entry-filter code is in `ENTRY_SKIP_REASONS`.
Size: S

### F9. Closed rule unions are duplicated, with a dead constant and two dispatch styles   [Low] [Confirmed] [Speculative]
Files: engine/strategy/config.py:140-156, engine/regime_gate.py:16-66, engine/stops.py:241-255, engine/strategy/config.py:146
Problem: `REGIME_RULES` (config.py:140) is never read; the rule names appear again as a `Literal` (config.py:147), an if-chain in `regime_allows_longs` and `__all__` in regime_gate.py. Stops dispatch through a planner dict; the regime gate through string comparisons. The strategy regime index is a `Literal` of two names, so a strategy gated on NIFTY MIDCAP needs a code change. Each is small; together they are the edit list for "new rule".
Fix: delete `REGIME_RULES`; give the regime gate the stop planners' shape (model class -> function dict, discriminated union on `rule`); validate `Regime.index` against the indices the store holds rather than a literal.
Tests: none new.

### F10. Four SMA implementations and two daily-data views for the same reads   [Low] [Confirmed] [Speculative]
Files: engine/criteria/indicators.py:31-39, engine/stops.py:153, engine/portfolio/regime.py:82-86, engine/regime_gate.py:22-32, daily/market.py:155-275, backtest/data.py:283-470
Problem: SMA is computed exactly in four places with different None/positivity rules (`regime_gate._sum` refuses a non-positive close, `regime.sma` does not). `DailyData` (live) and `MarketView` (backtest) each expose ATR, swing low, SMA, tick and previous close over the same pure helpers. They agree today, but the differences are where live and backtest drift (F2 is one case).
Fix: fold into F2's `DailySource` protocol; keep one exact `sma_sum` in `criteria/indicators.py` and have the stop, gate and regime code call it.
Tests: covered by F2's equivalence test.
Size: S (after F2)

## Suggested PRs
1. **Playbook kind from criteria** (F1, F8): derive playbook kind and unmodelled criteria from `data_needs`; branch scan, live pre-open and the backtest on it; compute `known_gaps` and `GAP_PLAYBOOKS` per config; the gap-scan minimum from `gap_up` params; `ENTRY_SKIP_REASONS` from the registry. Goal: a renamed or new gap playbook trades, and its unmodelled parts block the gate.
2. **One trigger-input builder** (F2, F10): a `DailySource` protocol over `DailyData` and `MarketView`, one `stop_inputs` and one entry-filter context builder, per-length ATR and swing live; one SMA. Goal: a new stop length or entry filter behaves the same in backtest and live and never switches off another bot's stops.
3. **One strategy identity** (F3), alongside or right after the consolidation PR: refuse a `bot` that is not the strategy's name (or drop it), plus a `create-strategy` admin command. Goal: a new strategy is a YAML file and one command.
4. **Generic levels** (F4): store every setup level, a validated level expression, one `resolve_level` for live and backtest. Goal: a new setup's level triggers without edits elsewhere.
5. **Portfolio follow-ups** (F5, F6, F7, F9): per-profile regime tables, a `single_sleeve_caps` known gap, split `versions.py` and rename the version states, regime-gate cleanup. Goal: a non-momentum sleeve fits, and the release path reads as one machine.
