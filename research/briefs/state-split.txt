Split hat_live: stock data only. Branch hat/state-split.

Owner rule (2026-10-26): hat_live is the canonical DB. It holds stock data only and is written only by data updates. Configs become versioned JSON files; trading state goes to a separate database. Owner approved both.

Today hat_live mixes three kinds of table (row counts 2026-10-26):
- Stock data, stays in hat_live: instruments, symbol history, ISIN lineage/merges/overrides, corporate actions (+versions), index members/membership, industries, market, trading calendar, price bands, announcements, demerger notices, broker symbol map, data quality checks/quarantine, universe + members + versions (derived from index data). Check each; anything the data pipeline writes stays.
- Config, moves to JSON: strategies (5) and strategy versions (6), risk policy versions (3, v3 in force), regime model versions, criterion types, bots (5), broker account (1), watchlist.
- Trading/runtime state, moves to a new database `hat_state` (same Postgres container): orders, fills, positions, signals, approvals, allocation, daily bot snapshots, exposure state, kill switch, mode changes, command log, job runs, telegram cursor/messages, trade results, holding baseline, broker sessions, regime state, signal announcements, events (hat_event partitions: classify; data-pipeline events stay with data only if the pipeline needs them), backtest run/bucket tables (empty; backtests write run folders now, PR hat/result-standard-backend; drop them from code).

Configs as JSON under HAT_DATA_ROOT/admin/config/<kind>/<id>/<version>.json (or a layout you justify), each validated against a schema on load, written atomically (temp + rename), never edited after publish: a new version is a new file; "in force" is a small pointer file per kind changed atomically, with history kept.
